# ADR: Components Follow Their Preferences

## Status

**Proposed** (Date: 2026-09-19)

## Context

Preferences are untyped string key/value pairs. Several derived states depend on them: cached tag patterns in `PatternConsts`, modification-info templates in `ModificationInfoManager`, view and tag-validation flags in `EditorSettings`, auto-completer key bindings in `AutoCompleter`, auto-spellcheck state.

Until now, whoever wrote such a preference had to know which derived state to refresh afterwards. Preferences dialog controllers did this in `persist()`: reset pattern caches, reset templates, call `updateViewPreferences()`, `updateTagValidationPreferences()`, `setAutoSpellChecking()`, `resetKeys()`. Any other writer (scripts, plugins, panel controls) had to duplicate that list or silently leave stale state. Duplicated lists drift: dialog and callers disagree on defaults and on which refresh belongs to which key.

`Preferences` already offers `addPropertyChangeListener(key, listener)`; `SaveThread` already uses it for the auto-save interval.

## Decision

Derived state subscribes to its own preference keys. Writers only write.

- `PatternConsts`: static listeners invalidate placeholder, custom-tag, remove pattern caches on their keys.
- `ModificationInfoManager`: static listeners rebuild templates on template keys.
- `EditorSettings`: constructor subscribes to view option and tag validation keys (debounced redraw via Swing timer: a page saved key by key from a worker thread redraws once), `USE_TAB_TO_ADVANCE` (field update), `ALLOW_AUTO_SPELLCHECKING` (on switch to on with project loaded: spellchecker re-init on caller's thread, then editor switch on EDT). Reactions run only on the live editor (`Core.getEditor() == parent`); stale instances stay silent.
- `AutoCompleter`: constructor subscribes to `AC_SHOW_SUGGESTIONS_AUTOMATICALLY`, `AC_SWITCH_VIEWS_WITH_LR`, rebinding keys on Swing thread.
- Dialog controllers `ViewOptions`, `Spellchecker`, `TagProcessing`, `AutoCompleter`, `General` lose their refresh calls; `General` writes `USE_TAB_TO_ADVANCE` directly.

Listeners may fire on any thread (dialog saves in `SwingWorker`); Swing reactions hop via `invokeLater`. Public refresh methods (`updateViewPreferences()` etc.) stay for callers that changed state without preferences.

Out of scope, stays in dialog: project reload prompt for `EXT_TMX_KEEP_FOREIGN_MATCH` (needs user consent), restart hint for theme keys, font event for font keys (dialog builds font object; one event, low drift risk), spellchecker reload while checking stays on (dictionaries installed on that page are no preference). `MARK_*` setters of `EditorSettings` untouched: they are menu-driven and already refresh themselves.

## Alternatives Considered

- Keep refresh calls in controllers, duplicate list in every other writer: rejected, drifts (observed: twelve default mismatches, one missing pattern reset in a panel module).
- Central reaction table in core keyed by preference: single copy, but still a table separate from the consumer; rejected in favour of consumers subscribing themselves.
- Typed preference descriptors carrying default, label, reaction: right long-term shape, too large for this step; deferred.

## Consequences

Note: ADR numbers 2026005 to 2026011 are taken by open branches.

- Scripts, plugins, panel controls get correct live behaviour by setting preference only.
- One source of truth per derived state; no refresh lists to keep in sync.
- Dialog `Apply` may redraw once per page instead of once per controller; coalescing keeps it to one document reload.
- Listener registration in constructors of `EditorSettings`, `AutoCompleter`: instances live as long as application; no unregistration needed. Tests creating many instances leak listeners (acceptable, mirrors existing `CoreEvents` usage).
- Follow-up: typed preference descriptors (key, default, label key) would remove remaining default duplication between dialog controllers and other writers.

## Verification

- `PreferenceListenersTest`: pattern caches and templates follow preference changes without explicit reset.
- `PreferenceListenerContractTest`: keys written by View and Tag Processing pages equal the keys `EditorSettings` subscribes to; no preferences dialog controller calls a refresh method any more.
- `EditorControllerTest` unchanged and green; editor redraw path exercised manually via preferences dialog.
